# Harness Guide

A practical guide to building an effective AI harness for a Claude Code–based workflow.

Sources: [Building effective agents](https://www.anthropic.com/research/building-effective-agents) ·
[Claude Code Memory](https://code.claude.com/docs/en/memory) ·
[Claude Code Skills](https://code.claude.com/docs/en/skills) ·
[Claude Code Hooks](https://code.claude.com/docs/en/hooks)

---

## What "harness" means

**Agent = Model + Harness.**

The model is the engine. The harness is everything else: context, tools, hooks, rules,
observability. Agent behavior is determined mostly by the harness, not by model choice.

Harness components in Claude Code:

| Component | Where it lives | What it does |
|-----------|-----------------|--------------|
| Static instructions | `CLAUDE.md`, `.claude/rules/*.md` | Always in context |
| Path-scoped instructions | `.claude/rules/*.md` with `paths:` | Loaded only when Claude works with matching files |
| Skills | `.claude/skills/*/SKILL.md` | Loaded on explicit call or when the agent judges them relevant |
| Hooks | `.claude/settings.json` → `hooks` | Deterministic code on lifecycle events |
| Permissions | `.claude/settings.json` → `permissions` | What the agent can do without confirmation |
| Auto memory | `~/.claude/projects/<repo>/memory/` | The agent writes it itself, reads it every session |

## Enforcement hierarchy

```
CI (GitHub Actions, etc.)
  └─ pre-commit hooks       (ruff, mypy — block the commit)
       └─ Claude Code hooks (settings.json — block the tool call)
            └─ .claude/rules/*.md  (MUST / MUST-UNLESS / PREFER)
                 └─ CLAUDE.md prose  (requests the agent can violate)
```

**Rule:** push every requirement as high up this ladder as it will go. A requirement that
exists only as prose in `CLAUDE.md` will eventually be violated.

### Where to place a given requirement

| Requirement | Where it belongs |
|-------------|-------------------|
| Never commit with ruff errors | pre-commit hook |
| Never commit with mypy errors | pre-commit hook |
| Never run `rm -rf` without confirmation | `permissions.deny` in `settings.json` |
| Run `make check` after changes | `[MUST]` in `CLAUDE.md` + `PostToolUse` hook |
| Test naming convention | `[MUST]` in `testing.md` |
| Prefer `pathlib` | `[PREFER]` in `python-core.md` |

## Context layers

### 1. Static context — CLAUDE.md + always-on rules

Loaded in every session. Always costs tokens.

**Belongs here:**
- Project commands (`make check`, `make fix`)
- Architectural decisions the agent would otherwise re-litigate
- Explicit prohibitions (`[MUST]` rules)
- Stack and project structure description

**Does NOT belong here:**
- Procedural instructions (setup, deployment) → Skills
- Conventions specific to one part of the codebase → path-scoped rules
- Context for the current task only → the conversation

**Target size:** ≤ 200 lines per file. Longer files start getting ignored.

### 2. Path-scoped rules

Rules in `.claude/rules/` support YAML frontmatter with a `paths:` field. The rule loads
only when Claude works with a file matching the pattern.

```markdown
---
paths:
  - "src/db/**/*.py"
  - "infrastructure/**/*.py"
---

# PostgreSQL & pgvector conventions
...
```

**Belongs here:** modules specific to one part of the codebase — pgvector rules scoped to
`src/db/`, data-engineering scoped to `etl/`, clean-architecture if layers are physically
separated by directory.

**Payoff:** tokens are spent only when the agent is actually working with that code.

### 3. Skills — on-demand context

Skills load on explicit invocation (e.g. `/workflow-scaffolding`) or when the agent judges
them relevant via `description` and `when_to_use` in the frontmatter.

```
.claude/skills/
├── workflow-scaffolding/
│   └── SKILL.md
└── audit-diff/
    └── SKILL.md
```

```yaml
---
name: audit-diff
description: Audit a diff generated by another agent/model against a fixed checklist.
when_to_use: reviewing a diff generated by another agent/model, dual review, pre-merge audit
---
```

**Belongs here:** procedural instructions (one-off or rare), long checklists, docs for
specific workflows. If a `CLAUDE.md` section has grown into a procedure, move it into a
Skill.

**Payoff:** the Skill body loads only when used — long content doesn't take up space in
every session.

### 4. Deterministic enforcement — hooks

Hooks are shell commands run on lifecycle events. They execute independently of what the
agent decides to do.

Configured in `.claude/settings.json`; see `project-template/.claude/settings.json` for the
live example this template ships — a `PostToolUse` hook on `Edit|Write` running
`.claude/hooks/lint-on-edit.sh` (30s timeout), and a `SessionStart` hook running
`.claude/hooks/warn-non-anthropic.sh`.

The hook scripts themselves live in `project-template/.claude/hooks/`:

- **`lint-on-edit.sh`** — reads JSON on stdin, extracts `tool_input.file_path`, and runs
  `uv run ruff check --fix` on it if it's a `.py` file. Guards on `jq`/`uv` being present
  and always exits 0 — advisory only, never blocks the session.
- **`warn-non-anthropic.sh`** — `SessionStart` hook; if `$ANTHROPIC_BASE_URL` is set,
  prints a warning that this session is not on the native Anthropic endpoint, so an audit
  shouldn't run here (see "Provider switcher" below).

**Key events:**

| Event | Fires when | Typical use |
|-------|------------|-------------|
| `PreToolUse` | Before a tool runs | Block dangerous commands |
| `PostToolUse` | After a tool runs | Lint after a file edit |
| `SessionStart` | Session starts | Check environment, surface reminders |
| `Stop` | Agent finishes | Remind to run `make check` |

**Pre-commit vs. Claude hooks:**
- Pre-commit blocks **`git commit`** — works independently of any agent.
- Claude hooks fire during **agent work** — finer-grained control.
- You want both: pre-commit is the safety net; Claude hooks are the in-session feedback loop.

## Project setup

```bash
./new-project.sh <target-dir> [module ...]   # defaults: python-core testing documentation
./new-project.sh --list                      # see available modules
```

The script copies `project-template/` into `<target-dir>` (never overwriting files already
there), copies the requested rule modules from `rules-library/` into `.claude/rules/`
(always including `_LEVELS.md`), removes the `_PUT_MODULES_HERE.txt` placeholder, and runs
`git init` if needed. It does **not** run `make install` itself — a fresh target has no
`pyproject.toml` yet.

Finish by hand in `<target-dir>`:
1. Fill in the `CLAUDE.md` TODOs — project description, active modules, architecture
   divergences, commands.
2. Review `.github/workflows/ci.yml` — add service containers (Postgres, Redis, ...) if the
   project needs one; the template ships a single `check` job (`checkout` → `setup-uv` →
   `uv sync --all-extras` → `make check`) and nothing project-specific.
3. Review `.claude/settings.json` — `permissions.allow`/`deny` for this project.
4. `make install && make install-hooks`.

## Dual-review protocol

Formalized as the `audit-diff` Skill (`project-template/.claude/skills/audit-diff/SKILL.md`,
also installed at `~/.claude/skills/audit-diff/` so it's available in any existing project
without touching that project's own files).

**When it runs:** invoke it explicitly (`/audit-diff` or by name) once a diff exists to
review. The skill itself applies a size/risk threshold — if the diff is under ~100 lines and
touches none of async code, SQL/migrations, concurrency, or a security-relevant surface, it
says `make check` is sufficient and stops. Dual review is for the diffs where a second,
independent pass actually catches something a single pass would miss.

**How it runs:** in a fresh session, on the Anthropic endpoint only. The skill's first step
is a hard gate: it checks `$ANTHROPIC_BASE_URL` and refuses to proceed if it's set to a
non-Anthropic provider — otherwise the generator and the auditor can silently turn out to be
the same underlying model, and "dual review" becomes double payment for one pass.

**What it checks:** a fixed checklist drawn from this repo's own MUST rules — blocking I/O
in async paths, lazy loading under `AsyncSession`, business logic leaking into routers,
bare `except`/raw exceptions crossing layer boundaries, mutable defaults, error-path test
coverage, migrations reviewed by hand, untrusted-input and secret handling — plus a
mandatory mechanical check (`make check` or lint+type+test separately).

**What comes out:** findings ordered by severity, each as `file:line` + the concrete failure
scenario, ending in an explicit **approve** or **fix-first** verdict.

## Provider switcher

The `cc-anthropic` / `cc-deepseek` / `cc-which` functions in `~/.zshrc` swap the active
Claude Code provider for the current shell (API key from Keychain, model env vars).

**Role split, not blanket cost-saving:** draft generation and mechanical work are cheap on
DeepSeek; audits and architecture decisions need the strongest model, on the native
Anthropic endpoint. Running an audit on `cc-deepseek` doesn't just risk a weaker review — if
the same model also generated the diff, dual review provides no independent signal at all.

**Safety net:** the provider switcher is shell-global state, so it's easy to start an audit
session without noticing `cc-deepseek` is still active from earlier work. The
`warn-non-anthropic.sh` `SessionStart` hook (see above) and the `audit-diff` skill's endpoint
gate both catch this — the hook warns, the skill refuses outright.

## Enforcement before expansion

When enforcement is incomplete (`hooks: {}`, no CI, no `make check`), fix that before adding
more rules, Skills, or MCP servers. An unenforced rule is prose, and prose gets violated
under time pressure exactly when it matters most. This repo's own rollout followed that
order: rollout script and CI/hooks before the audit contract, the audit contract before
deduplicating docs.

## Day-to-day workflow

**Think of the agent as a junior developer with good onboarding:**

- `CLAUDE.md` = onboarding doc: stack, commands, architecture, prohibitions.
- Rules = coding standards: what to do in each situation.
- Skills = playbooks: how to run a specific operation.
- Hooks = CI on steroids: automatic checks after every action.

**In practice:**

1. Start a task with context in the prompt: what you're doing, which files are involved.
2. After changes, have the agent run `make check` itself (if that's a `[MUST]` in
   `CLAUDE.md`).
3. If the agent keeps doing something wrong, add it to `CLAUDE.md` or a rule file instead of
   repeating the instruction every time.
4. For one-off tasks (deployment, schema refactor), invoke a Skill explicitly: `/skill-name`.

## Session management and multi-agent workflow

Session context is a resource. As history grows, earlier instructions lose weight
(attention dilution). Mixing work phases in one session degrades each of them.

### Split phases across sessions

| Phase | Why a separate session |
|-------|--------------------------|
| **Planning** | A planning agent shouldn't see implementation detail — that creates confirmation bias. Use `/plan` or a separate session for architectural decisions. |
| **Implementation** | Start a fresh session with the plan as a document (paste it into the prompt or a file). The agent doesn't carry the weight of the prior discussion. |
| **Review** | The agent that wrote the code will defend its own decisions on review. Run `/code-review` (or the `audit-diff` skill) in a separate session, giving it only the diff — not the implementation history. |
| **Research** | A long codebase search pollutes context. Use a subagent (Explore) and bring back a short report into the main session. |

### Rule: the plan outlives the session, the context doesn't

If a decision matters, write it down:
- Architectural decision → `CLAUDE.md` ("Key design decisions") or `DECISIONS.md`.
- Coding convention → `.claude/rules/*.md`.
- Task-local context → the next session's prompt.

Don't rely on the agent "remembering" a previous session. It doesn't.

### When to use a subagent

Launch a subagent (`Agent` tool, Explore, Plan, general-purpose) when:
- You need to explore an unfamiliar part of the codebase without polluting the main context.
- You want an independent look (review after implementation — a different agent, no history).
- The task parallelizes (several independent investigations at once).
- The subagent's answer will be long — get a short summary back, not the full output.

**Don't** launch a subagent for quick lookups (grep, reading one file) — that costs more
than calling the tool directly.

### `/compact` as a control tool

When context grows mid-task, `/compact` condenses history while keeping key facts. Use it
when:
- Debugging took many iterations and a final fix is in place.
- The research phase is done and implementation is starting.
- The context window is more than ~70% full.

After `/compact`, confirm `CLAUDE.md` and rules reloaded — they're recomputed automatically
on compaction.

## Token economics

Every token in static context is paid **every** session. At 50 sessions/day × a 200-line
`CLAUDE.md`, that's a real recurring cost.

**Economy principles:**

| Content | Optimal location |
|---------|-------------------|
| Always needed | `CLAUDE.md` / always-on rules |
| Needed for part of the codebase | path-scoped rules |
| Needed for specific tasks | Skills |
| Needed once | the conversation |

**Signs static context is overloaded:**
- `CLAUDE.md` > 200 lines.
- Rule files containing procedural instructions ("first do X, then Y").
- The agent starts ignoring rules from the middle of a file.

**Fix:** move procedural content into Skills, codebase-specific content into path-scoped
rules. Static context should be facts and prohibitions, not instructions.
